# SDK 0.8.0 Completion and Async Parity Design

## Goal

Release `kite-algo-worker==0.8.0` as the complete, typed client contract for the public worker API. The release closes the remaining synchronous execution-observability gaps, gives the asynchronous client the same supported operations, and adds an automated contract check so backend and SDK coverage cannot silently drift again.

This release is the prerequisite for a separate Kite Algo MCP server. MCP will depend on the public SDK and will not call broker, database, paper-runtime, or backend-internal services directly.

## Current state

The mounted backend currently exposes:

- 77 worker HTTP method/path operations across 71 paths
- 3 worker WebSocket routes
- 67 of 77 worker HTTP operations through `KiteAlgoWorkerClient`
- 33 of 77 worker HTTP operations through `AsyncKiteAlgoWorkerClient`
- all 3 worker WebSocket routes through `WorkerWebSocketClient`

The synchronous gaps are concentrated in execution observability and lifecycle recovery. The asynchronous client is a useful partial client, but its name currently implies broader equivalence than it provides.

## Design principles

1. The SDK remains limited to `/api/algo-workers/worker/*` and the corresponding worker WebSocket routes.
2. Strategy code owns decisions; the platform continues to own execution, attribution, accounting, safety, and protection truth.
3. Sync and async clients expose equivalent domain operations unless a transport capability is explicitly documented as different.
4. Mutating calls preserve idempotency, safety-token, and worker-session requirements. The SDK does not weaken backend enforcement.
5. Public helpers stay explicit and typed. There will be no generic public `request(path, payload)` escape hatch.
6. MCP remains a separate adapter over the SDK rather than becoming part of the SDK package.

## Scope

### Synchronous completion

Add public synchronous methods for the ten uncovered operations:

- `get_order_history(...)`
- `list_baskets(...)`
- `get_basket(...)`
- `create_bracket(...)`
- `list_brackets(...)`
- `get_bracket(...)`
- `cancel_bracket(...)`
- `list_execution_events(...)`
- `stream_execution_events(...)`
- `export_fundamentals_csv(...)`

These method names are the public 0.8.0 contract. Existing naming conventions still apply to any additional typed `*_snapshot` helpers.

### Typed response contracts

Add or refine models for:

- order-history responses and individual order events
- basket execution summaries and per-leg results
- bracket intent state, child-order state, and cancellation results
- execution-event pages and individual execution events

JSON methods should provide both the established raw-dictionary style where compatibility requires it and typed `*_snapshot` methods where that is the current convention.

`export_fundamentals_csv(...)` is a non-JSON operation. It returns CSV content as text or bytes and uses a text-response transport path rather than wrapping the response in `{"raw": ...}`. Writing the CSV to disk is the caller's responsibility.

### Async parity

`AsyncKiteAlgoWorkerClient` will support the same 77 worker HTTP operations as `KiteAlgoWorkerClient`, including:

- worker and run heartbeats
- run creation, session claim/release, and exit
- safety checks, risk updates, and backend protection updates
- order placement, basket placement, order cancellation, and order modification
- order history, basket state, bracket lifecycle, and execution events
- asynchronous SSE iteration for ticks, candles, P&L, timeline, and execution events
- the complete options namespace through an async options client
- fundamentals CSV export

The existing `WorkerWebSocketClient` remains the shared asynchronous WebSocket surface. The HTTP async client may expose a convenient factory/property for it, but WebSocket logic will not be duplicated.

### Shared internals

Avoid a broad rewrite of the working synchronous client. Extract shared logic where it prevents real sync/async drift:

- URL and endpoint path construction
- instrument splitting and normalization
- historical date parameter construction
- fundamentals scope validation
- request payload construction for runs, intents, risk, protection, and exits
- response model parsing
- endpoint inventory metadata

Keep transport-specific behavior separate:

- synchronous JSON, text, and SSE transport uses `requests`
- asynchronous JSON, text, and SSE transport uses `httpx`
- WebSocket transport continues to use `websockets`

The public clients remain ordinary explicit Python APIs. Shared internals must not force callers to understand endpoint descriptors or transport objects.

## Contract coverage guard

Add a repository-level contract test that generates the mounted FastAPI OpenAPI document and selects every HTTP operation under `/api/algo-workers/worker/*`.

Maintain a small SDK endpoint manifest containing, for each operation:

- HTTP method
- normalized path template
- synchronous public method
- asynchronous public method
- response kind: JSON, text, or SSE
- mutation classification

The test fails when:

- a backend worker operation has no manifest entry
- a manifest entry references a missing public SDK method
- sync or async coverage is absent without an explicit reviewed exception
- an SDK endpoint no longer exists in the backend contract

Exceptions must include a reason and should normally be empty for HTTP operations after 0.8.0. WebSocket coverage receives a parallel assertion against the three mounted worker WebSocket routes.

The manifest is a test and maintenance contract. It must not be used to automatically expose every operation as an MCP tool.

## Error handling and reliability

All new methods use the existing SDK exception hierarchy and preserve backend response details.

- Authentication and authorization failures remain distinct from validation, conflict, safety, and service-availability failures.
- SSE methods close connections deterministically and surface invalid events as SDK errors.
- Async streaming supports cancellation without leaking the HTTP response or client.
- Mutating operations are not automatically retried.
- A future retry policy may cover idempotent reads, but retry behavior is not required for this release.

## Testing

### Method-level tests

For every new sync and async method, verify:

- HTTP verb and URL
- query parameters, payload, and required headers
- typed response parsing
- backend error translation

### Lifecycle tests

Cover representative workflows rather than only isolated methods:

1. create run, claim session, safety check, submit order, inspect order history, and release session
2. submit basket and recover basket execution state
3. create bracket, inspect it, and cancel remaining children
4. consume execution-event history and its SSE continuation
5. execute the equivalent workflows through the async client

### Contract tests

- enforce 77 of 77 sync HTTP operations
- enforce 77 of 77 async HTTP operations
- enforce 3 of 3 worker WebSocket routes
- verify all declared response models against representative fixtures

### Release verification

Run the full release-relevant SDK suite, route-mount checks, version-reference check, package build, and package metadata validation before tagging 0.8.0.

## Documentation

Update the canonical SDK README, conceptual worker guide, and agent-context guide to include:

- execution-event inspection and streaming
- basket recovery and state inspection
- bracket lifecycle
- order history
- fundamentals CSV export
- sync/async capability parity

Examples should remain safe by default. Add at most one recovery/observability example if it teaches a workflow not already represented by the canonical examples.

## Out of scope

- wrapping application auth, system, journal, analytics, ingestion, mutual-fund, or UI-oriented endpoints
- direct broker or database access
- changing backend trading behavior
- automatic retry of trading mutations
- automatic SDK generation from the entire application OpenAPI document
- MCP server implementation
- LLM-driven trading decisions

## Follow-on MCP project

After 0.8.0 is released, design `kite-algo-mcp` as a separate package or deployable service that depends on the SDK.

The first MCP release should be read-only and expose a curated set of market, portfolio, run-state, P&L, order, safety, and execution-event capabilities. Preview tools may be considered read-only only when the backend guarantees that they cannot place orders. Trading mutations require a separate design for identity, scopes, confirmation, audit logging, idempotency, and live-mode controls.

Local development may begin with stdio. Remote deployment should use the then-current MCP Streamable HTTP transport and its authorization requirements. Exact MCP SDK and protocol versions will be selected and pinned during the separate MCP design because that ecosystem evolves independently of `kite-algo-worker`.

## Completion criteria

SDK 0.8.0 is complete when:

1. all 77 worker HTTP operations are covered by both public clients
2. all 3 worker WebSocket routes remain covered
3. execution lifecycle responses have stable typed models and fixtures
4. contract drift causes CI to fail
5. docs and examples describe the released surface accurately
6. package build and release checks pass
7. no non-worker backend surface or MCP implementation has leaked into the SDK
